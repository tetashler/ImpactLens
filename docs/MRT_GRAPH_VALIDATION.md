## Decision

Not validated for timetable-accurate journey planning or policy impact claims.** The baseline is fully connected after two evidenced interchange consolidations and explicit line transfers. ## Travel-time model and valid trips

1. Select active service IDs using weekly calendar, inclusive start/end dates and calendar_dates additions/removals. No service outside the calendars is inferred from feed_info.
2. Validate trip references, platform parents, stop-sequence uniqueness and nonnegative dwell/positive run times. Reject an entire invalid trip and record its source rows; never bridge past a rejected stop record.
3. Quarantine an entire trip if it contains a reviewed suspicious pair. The audit scans all services, including trips inactive on the baseline date. Original values remain untouched.
4. For each consecutive accepted pair on the same line, compute **arrival at next stop minus arrival at current stop**, equal to current-stop dwell plus running time. Use its median across active accepted trips. For even sample counts, average the two middle observations; run/dwell decomposition uses those same observations. All contributing trip and stop-time row references are exported.
5. Dijkstra minimises those static edge costs plus explicit transfers. Boarding any line at the origin costs an initial 120 seconds; a zero-distance query costs zero. Arrival at the destination ends the journey without a final transfer or destination dwell.

This arrival-to-arrival convention includes initial-stop dwell in addition to the initial wait. It is an explicit approximation and can slightly overstate origin time. Medians combine different trips and times of day, do not preserve headways, and do not guarantee a feasible same-train sequence. Branch service, direction changes within a line, short workings, operating hours, late-night connections, missed trains, crowding and reliability are not modelled. Walking to/from the station is excluded. No passenger weighting is applied. Times are estimates under this model, not predictions of current operations.

## Timetable validity and provenance

feed_info asserts LTA publisher, version 0.1 and 2025-01-01–2026-12-31 coverage. All six actual calendar rows cover only 2026-01-01–2026-12-31. There is no 2025 service or defined service after 2026. SERVICE_WE runs Saturday; SERVICE_PH runs Sunday; the names do not implement public-holiday behaviour, and calendar_dates has no exception records. A valid service date does not independently establish commissioning dates or current operating status.

GTFS values above 24:00 remain seconds since the service-day origin; they are not reset to zero. The source feed's exact download location, creator, generation method, licence and official timetable status remain **unverified**. Publisher text is not authentication. Public searches for distinctive trip IDs did not establish provenance. The prototype neither fetches nor substitutes a different community feed. Obtain the original download URL/archive and generation notes before treating the schedule as authoritative.

## Automated verification and limits

Run `npm.cmd test` on Windows (`npm test` elsewhere). Tests cover quoted/multiline CSV and physical row references, next-day times, calendars and exceptions, whole-trip rejection/quarantine, explicit aliases and transfers, manual route costs, unreachable/unknown nodes, invalid weights, and CLI argument/read-only behaviour. Real-data tests cover three service dates and compare every origin-station-to-routing-state Dijkstra distance with an independent Floyd-Warshall implementation. Predecessor costs, route continuity, representative path endpoints, all-pair reachability and raw BPLRT disconnection are checked. Input hashes are checked after graph construction. Passing tests establish software/model consistency, not real-world calibration.

## Reproduce and inspect

```powershell
npm.cmd test
npm.cmd run mrt:validate
npm.cmd run mrt:validate -- --date 2026-10-31
npm.cmd run mrt:report
```

Validation is read-only by default. The explicit `--write` flag regenerates this report and owned derived JSON files under `data/derived/mrt/`. No raw input is written. Paths resolve from the CLI's project directory, independent of the shell's working directory.

- `baseline-2026-10-27.json`: catalogue, aliases, service states, directed edges, source hashes and complete observation references. Each travel edge's sourceRefs tuple is **[trip_id, trips.txt physical line, from stop_times.txt physical line, to stop_times.txt physical line]**, header line 1. The trip row provides route_id/service_id; its route row supplies the line. Entrance/platform IDs and original station rows resolve through the unchanged stops file.
- `audit-2026-10-27.json`: metadata/calendars, all-service suspicious/invalid original rows, per-date connectivity checks and sample routes. Each sourceRow object carries the physical line and original field values.
- Static routing functions are importable from `prototype/mrt/routing.ts`; `buildGraph` accepts declared transfer/wait assumptions. Raw diagnostics are available through `mode: 'raw'`.
